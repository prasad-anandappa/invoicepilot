## 2. Persistence layer ✅ (with one plainly-stated substitution)

**No Postgres server exists on this machine**, so per the pack's fallback the layer is built on
SQLAlchemy 2.0 with **SQLite as the dev/test dialect and Postgres as the production dialect** —
identical models, `DATABASE_URL` picks the engine (`postgresql+psycopg://…` in production;
psycopg 3 driver is in `requirements.txt`). Nothing in the schema is SQLite-specific:
money is `Numeric`, payloads are JSON (JSONB variant on Postgres), PKs are app-generated
string UUIDs, timestamps are timezone-aware.

**Implemented:**

- `app/db.py` — SQLAlchemy models for all 9 pack tables: `users`, `business_profiles`
  (holds the per-owner invoice-number sequence), `clients`, `invoices`, `invoice_items`,
  `paypal_orders`, `reminders`, `agent_events`, `idempotency_keys`. `owner_id` on every
  tenant row; per-owner unique constraints on invoice ref/number, client name, and
  idempotency keys.
- `app/db_store.py` — `DbInvoiceStore` implementing the **exact surface of the in-memory
  `InvoiceStore`** (`next_number`, `add`, `by_idempotency_key`, `remember_idempotency_key`,
  `get`, `by_order`, `all`, plus an explicit `save()` persist point). Every query is scoped
  by the store's `owner_id` — cross-owner reads return nothing / raise `KeyError`, proven by
  test. Domain mapping: client find-or-create by (owner, name); invoice persisted as one
  aggregate line item; timeline stored in `agent_events`; reminders and the PayPal order as
  child rows; idempotency records keep a response snapshot so a replay returns the original
  response.
- **Migrations with a tested rollback path:** Alembic initialised (`migrations/`),
  env wired to the app's `DATABASE_URL`, initial revision autogenerated (one autogenerate
  quirk fixed by hand: bare `Text()` → `sa.Text()` in the JSONB variant). Verified round-trip:
  upgrade → all 9 tables; downgrade → clean; upgrade again → all 9 tables.
- `requirements.txt` — added `sqlalchemy`, `alembic`, `psycopg[binary]`.

**Persistence contract change (deliberate, documented in `db_store.py`):** the in-memory store
holds object references, so mutations are implicitly saved. The DB store persists on
`add()`/`save()` calls. Week-2 wires those save points into the agent/API flows when auth
lands; this week the in-memory store remains the API default and the 62 tests are untouched.
